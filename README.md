# Autonomous Drone Flight Telemetry & Failsafe Watchdog

A Linux-based C++ capstone project that demonstrates two simple safety mechanisms:

1. **Telemetry safety monitoring** — raw roll, pitch, yaw and altitude values are generated by a simulator, and the C++ program decides whether the current state is `NORMAL`, `WARNING` or `FAILSAFE`.
2. **Software liveness monitoring** — the C++ program sends a heartbeat to a Linux watchdog kernel module. When heartbeats stop, the driver detects a timeout.

> **Important:** This is an educational software simulation. It does not control a real drone, and the watchdog timeout does not reboot the development machine.

## Objectives

- Generate raw drone telemetry automatically.
- Evaluate roll, pitch and altitude against project safety limits.
- Maintain the states `NORMAL`, `WARNING` and `FAILSAFE`.
- Implement a Linux watchdog kernel module using the Linux Watchdog Driver Core and `hrtimer`.
- Send periodic watchdog heartbeats from the C++ application.
- Demonstrate watchdog timeout when the application intentionally stops sending heartbeats.

## Build

Build the C++ application:

```bash
make app
```

Build the unit tests:

```bash
make test
```

Build the kernel module:

```bash
make driver
```

To specify another kernel-header directory:

```bash
make driver KDIR=/lib/modules/$(uname -r)/build
```

Build everything:

```bash
make all
```

Clean generated files:

```bash
make clean
```

## Run

### 1. Load the watchdog driver

```bash
sudo insmod driver/drone_watchdog.ko
ls -l /dev/watchdog*
dmesg | tail -20
```

The watchdog device is normally `/dev/watchdog0`, but the actual number can vary.

### 2. Run automatic telemetry

This is the normal operating mode. The simulator produces **raw telemetry only**. It does not generate a ready-made safety label. The C++ safety monitor calculates the state from the values.

```bash
sudo ./bin/drone_monitor --cycles 15
```

The output shows telemetry, the calculated safety state, and watchdog heartbeats.

### 3. Run controlled tests

Controlled scenarios are included only so that the important behaviors can be demonstrated reliably during evaluation.

Warning test:

```bash
sudo ./bin/drone_monitor --scenario warning --cycles 8
```

Failsafe test:

```bash
sudo ./bin/drone_monitor --scenario failsafe --cycles 8
```

Watchdog timeout test:

```bash
sudo ./bin/drone_monitor --scenario watchdog --cycles 8
```

The watchdog test intentionally stops heartbeats for one cycle. The kernel timer should then report a timeout.

### 4. Unload the driver

```bash
sudo rmmod drone_watchdog
```

## Safety Rules Used in the Simulation

These are **project-defined simulation limits**, not real flight-control limits.

| Parameter | Normal | Warning | Failsafe |
|---|---|---|---|
| Roll | <= 20° | > 20° | > 45° |
| Pitch | <= 20° | > 20° | > 45° |
| Altitude | > 20 m | 5–20 m | <= 5 m |

Yaw is generated and displayed as part of telemetry, but no absolute yaw threshold is used because a heading value by itself is not inherently unsafe.

`FAILSAFE` has priority over `WARNING` when a critical condition is present.

## Watchdog Interface

The C++ application communicates with `/dev/watchdogN` using the standard Linux watchdog interface:

- `WDIOC_SETTIMEOUT` — configure timeout
- `WDIOC_SETOPTIONS` — start/stop watchdog
- `WDIOC_KEEPALIVE` — send heartbeat

A small project-specific status ioctl is also used so the demo can show timeout and heartbeat counters.

The kernel module is a **simulated hardware watchdog**: `hrtimer` models the countdown, while the Linux Watchdog Driver Core provides the watchdog device interface.

## Project Logic

```text
Raw telemetry
      |
      v
C++ Safety Monitor
      |
      +----> NORMAL
      +----> WARNING
      +----> FAILSAFE
      |
      v
Heartbeat
      |
      v
/dev/watchdog0
      |
      v
Kernel watchdog driver
      |
      +---- no heartbeat ----> timeout / simulated recovery event
```
